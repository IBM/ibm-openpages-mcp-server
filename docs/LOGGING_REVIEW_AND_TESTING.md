## Your Questions Answered

### 1. Environment Variable Configurations

You identified 4 logging-related environment variables. Let me clarify each:

#### A. `DEBUG` (Application-Level Debug Mode)
- **Location**: [`.env:5`](.env:5), [`settings.py:68`](../src/app/config/settings.py:68)
- **Type**: Boolean (`true`/`false`)
- **Purpose**: Controls **application behavior**, not just logging
- **Effects**:
  - When `DEBUG=true`:
    - Enables FastAPI auto-reload on code changes ([`main.py:211`](../main.py:211))
    - Can trigger additional debug features in application logic
    - Does NOT automatically change log level
  - When `DEBUG=false`:
    - Production mode
    - No auto-reload
    - Standard application behavior

**Key Point**: `DEBUG` is for **application development mode**, not logging level control.

#### B. `LOG_LEVEL` (Logging Level)
- **Location**: [`.env:41`](.env:41), [`settings.py:92`](../src/app/config/settings.py:92)
- **Type**: String (DEBUG, INFO, WARNING, ERROR, CRITICAL)
- **Purpose**: Controls **minimum log level** that will be output
- **Effects**:
  - `LOG_LEVEL=DEBUG`: Shows ALL logs (DEBUG, INFO, WARNING, ERROR, CRITICAL)
  - `LOG_LEVEL=INFO`: Shows INFO, WARNING, ERROR, CRITICAL (hides DEBUG)
  - `LOG_LEVEL=WARNING`: Shows WARNING, ERROR, CRITICAL (hides DEBUG, INFO)
  - `LOG_LEVEL=ERROR`: Shows ERROR, CRITICAL only
  - `LOG_LEVEL=CRITICAL`: Shows CRITICAL only

**Key Point**: `LOG_LEVEL` is the **primary control** for what gets logged.

#### C. `LOG_FORMAT` (Output Format)
- **Location**: [`.env:42`](.env:42), [`settings.py:93`](../src/app/config/settings.py:93)
- **Type**: String (`json` or `text`)
- **Purpose**: Controls **how logs are formatted**
- **Effects**:
  - `LOG_FORMAT=json`: Structured JSON format (machine-readable)
    ```json
    {"timestamp": "2026-01-08T12:48:02.612Z", "level": "INFO", "message": "...", ...}
    ```
  - `LOG_FORMAT=text`: Human-readable plain text
    ```
    2026-01-08 12:48:02 - module.name - INFO - message here
    ```

**Key Point**: `LOG_FORMAT` controls **presentation**, not content or level.

#### D. `LOG_FILE` (File Output Path)
- **Location**: [`.env:43`](.env:43), [`settings.py:94`](../src/app/config/settings.py:94)
- **Type**: String (file path) or `None`
- **Purpose**: Specifies **where to write logs** (in addition to console)
- **Effects**:
  - When set (e.g., `LOG_FILE=logs/grc-mcp.log`): Logs written to both console AND file
  - When `None` or empty: Logs only to console (stdout/stderr)
  - Relative paths resolved from project root
  - Directories auto-created if they don't exist

**Key Point**: `LOG_FILE` adds **file output**, doesn't replace console output.

### 2. Missing Fields in Your Logs

You observed that `request_id`, `user_id`, `session_id`, `duration`, and `status_code` are missing from some log entries. Here's why:

#### Context-Dependent Fields

These fields are **only present when relevant context exists**:

| Field | When Present | Example Log Lines |
|-------|--------------|-------------------|
| `request_id` | HTTP requests processed by [`ObservabilityMiddleware`](../src/app/observability/middleware.py:230) | Lines 26-100 in your log |
| `user_id` | When `X-User-ID` header is present | Not in your log (no auth) |
| `session_id` | When `X-Session-ID` header is present | Not in your log (no sessions) |
| `status_code` | Request completion logs | Lines 27, 29, 31, etc. |
| `duration_ms` | Request completion logs | Lines 27, 29, 31, etc. |

#### Why Some Logs Don't Have These Fields

**Startup Logs (Lines 1-25)**:
```json
{"timestamp": "2026-01-08T12:48:02.612228Z", "level": "INFO", "logger": "root", 
 "message": "Logging configured: level=INFO, format=JSON, service=grc-mcp-server"}
```
- No `request_id`: Not processing an HTTP request
- No `user_id`/`session_id`: No user context during startup
- No `duration`/`status_code`: Not a request completion

**Request Start Logs (Line 26)**:
```json
{"timestamp": "2026-01-08T12:48:11.692793Z", "level": "INFO", 
 "request_id": "cc20485e-8757-45bc-8c51-de6ecee31434",
 "message": "Request started: GET /metrics"}
```
- Has `request_id`: Generated by middleware
- No `status_code`/`duration`: Request just started, not completed yet

**Request Completion Logs (Line 27)**:
```json
{"timestamp": "2026-01-08T12:48:11.693688Z", "level": "INFO",
 "request_id": "cc20485e-8757-45bc-8c51-de6ecee31434",
 "status_code": 503, "duration_ms": 0.6918907165527344,
 "message": "Request completed: GET /metrics - 503 (0.001s)"}
```
- Has `request_id`, `status_code`, `duration_ms`: Request completed

#### How to Get User/Session IDs

These require **client-side headers**:

```bash
# Test with user and session IDs
curl -H "X-User-ID: user123" \
     -H "X-Session-ID: session456" \
     http://localhost:8000/health
```

Then your logs will show:
```json
{
  "request_id": "...",
  "user_id": "user123",
  "session_id": "session456",
  ...
}
```

3. **HTTP library logs are suppressed** ([`logger.py:261-264`](../src/app/observability/logger.py:261-264)):
   ```python

   logging.getLogger("httpx").setLevel(logging.INFO)
   ```

## Common Issues and Solutions

### Issue 1: No DEBUG Logs Appearing

**Symptom**: `LOG_LEVEL=DEBUG` but no DEBUG logs

**Causes**:
1. Code doesn't use `logger.debug()`
2. HTTP libraries suppressed (intentional)

**Solution**: Add DEBUG logs to your code:
```python
logger.debug("Detailed info here", extra_fields={"data": value})
```

### Issue 2: Missing Context Fields

**Symptom**: No `request_id`, `user_id`, `session_id`

**Causes**:
1. Not in HTTP request context
2. Headers not provided

**Solution**: 
- For HTTP requests: Middleware adds `request_id` automatically
- For user/session: Client must send headers

### Issue 3: Logs Not in File

**Symptom**: Console shows logs but file is empty

**Causes**:
1. File path incorrect
2. Permission issues
3. Directory doesn't exist

**Solution**:
```python
# Check in logger.py:268-285
# Directories are auto-created
# Check file permissions
ls -la logs/
```
